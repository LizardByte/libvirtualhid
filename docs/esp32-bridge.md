# ESP32-S3 USB bridge

The `esp32_bridge` backend creates devices on an ESP32-S3 connected to the host
over USB. The board enumerates as a composite USB device: a CDC-ACM serial port
that the backend talks to, plus up to two device slots. The operating system
binds its inbox drivers to the slots (`xusb22` for XInput, `hidclass` or the
kernel HID drivers for HID).

Firmware, a browser flasher, and supported boards are maintained in
[esp32s3-hid-bridge](https://github.com/cheetahdotcat/esp32s3-hid-bridge). The
wire protocol is defined in `src/platform/esp32/esp32_bridge_protocol.hpp`; the
firmware keeps a C copy of it.

## Selecting the backend

Set `RuntimeOptions::backend` to `BackendKind::esp32_bridge`, or let
`BackendKind::platform_default` select the bridge:

| Condition (checked in order)                       | Backend used      |
|----------------------------------------------------|-------------------|
| `esp32_bridge.autodetect` is `false`               | platform          |
| `LVH_BACKEND=platform`                             | platform          |
| `LVH_BACKEND=esp32_bridge`                         | bridge            |
| `LVH_ESP32_PORT` or `esp32_bridge.port` is set     | bridge, that port |
| A port with USB serial number `LVHB-*` is attached | bridge            |
| Otherwise                                          | platform          |

Detection runs once, when the runtime is created. Applications that let users
choose the bridge explicitly should set `esp32_bridge.autodetect = false`.
`LVH_ESP32_PORT` also overrides the port for `BackendKind::esp32_bridge`. When
`platform_default` selected the bridge and no bridge answers, gamepads fall
back to the platform backend.
`lvh::find_esp32_bridge_ports()` lists attached bridges without opening them.
Port discovery is available on Linux and Windows; other platforms need an
explicit port.

## Slots and profiles

The ESP32-S3 USB controller limits the bridge to two slots next to the serial
port. Keyboard and mouse share one slot; each gamepad takes one.

| Slot A         | Slot B                  |
|----------------|-------------------------|
| keyboard+mouse | none or one gamepad     |
| Xbox           | PlayStation or Switch   |
| PlayStation    | same PlayStation family |

| Requested profile          | Slot type                                         | USB identity     |
|----------------------------|---------------------------------------------------|------------------|
| Xbox 360, One, Series      | XInput (`XUSB10` compatible ID)                   | bridge VID/PID   |
| Generic                    | XInput                                            | bridge VID/PID   |
| DualSense                  | HID with cached feature reports                   | `054C:0CE6`      |
| DualShock 4                | HID with cached feature reports                   | `054C:09CC`      |
| Switch Pro                 | HID; subcommand replies generated by the backend  | `057E:2009`      |
| Keyboard, mouse            | HID keyboard, relative and absolute pointer       | bridge VID/PID   |

Every slot change re-enumerates the whole bridge, so other devices disconnect
for about one second. `create_gamepad()` returns after the bridge is back.
Keyboard and mouse reports are queued in order and never replayed after a
reconnect; the latest gamepad report is.

Text that is not US-ASCII, and keyboard or mouse requests when both slots are
taken, go to the platform backend. Touchscreen, trackpad, and pen tablet
devices are not available.

## Pairing

The bridge accepts devices and input only from paired hosts, unless pairing
was turned off on the bridge.

- When a host connects without a stored pairing, the backend asks the bridge to
  pair and logs a warning. The user confirms by pressing BOOT on the bridge.
  Devices created before that succeed; they appear once pairing completes.
- The bridge returns a secret, which the backend stores per bridge in
  `esp32_bridge.credential_dir` (default `%ProgramData%\libvirtualhid\esp32-bridge`
  on Windows, `$XDG_CONFIG_HOME/libvirtualhid/esp32-bridge` elsewhere). Only the
  file owner, and on Windows SYSTEM and Administrators, can read it.
- Each connection authenticates with HMAC-SHA256 over a fresh challenge.
- `esp32_bridge.client_name` labels the pairing on the bridge.
- `lvh::esp32_bridge_status()` reports whether the bridge is connected or waits
  for the BOOT button.

Pairing keeps other non-administrator programs from sending input through the
bridge. It does not protect against software running as administrator.

## Troubleshooting

| Problem                                   | Fix                                                                     |
|-------------------------------------------|-------------------------------------------------------------------------|
| `no ESP32-S3 bridge answered`             | Check the cable and that the board runs the bridge firmware.            |
| `bridge firmware speaks a different ...`  | Flash firmware that matches this libvirtualhid version.                 |
| `bridge is not paired with this host`     | Press BOOT on the bridge while its LED blinks quickly.                  |
| Devices disappear for a second            | Expected when a device is added or removed.                             |
| A second gamepad fails to appear          | Both slots are in use, or the combination is not in the table above.    |
